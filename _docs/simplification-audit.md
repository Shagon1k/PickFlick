## Решения (2026-10-28)

1. **#2 — да**, если функциональность не теряется. Продуктовая функциональность не теряется:
   таблицу никто не читает. Пропадает только история каждой попытки (время и причина каждой
   неудачи) в БД. В `NotificationEmailDelivery` остаются счётчик, время первой попытки и последняя
   причина, а каждая попытка по-прежнему пишется в структурный лог (`email.retry_scheduled`). Запрос
   по попыткам в `_docs/email-delivery.md` перевести на `NotificationEmailDelivery."attemptCount"`.
   Формулировку ROADMAP «delivery attempts» уточнить.
2. **#3 — да.**
3. **#14 — одно правило, как в Library.**
4. **#7 — как читабельнее:** см. уточнение в разделе H (#49).
5. **#10 — да, в минимальном варианте.** Полностью убирать нельзя: в отличие от обычной Session,
   повтор Past Session ничего не блокирует, а завершённую Session удалить нельзя. При потерянном
   ответе получится неудаляемый дубль. Оставляем `submissionId`, но при повторе просто возвращаем
   уже созданную Session того же Club, без сравнения всех полей (~80 строк уходят).
   **Пересмотрено при реализации:** journey `past-session.spec.ts` и фикс ревью PR #186 (раунд 2)
   показали, что без сравнения правки после потерянного ответа молча терялись бы. Сравнение
   оставлено, но переписано: одна функция `assertSameSubmission` сравнивает два канонических
   отпечатка (`past-session-replay.ts`) вместо проверок по полям в двух файлах.
6. **#19 — оставить как есть.**
7. **#27 — принято:** убрать mock-спеки, дублирующие journeys по happy path,
   а mock оставить для `@visual` и состояний, которые реальный бэкенд воспроизводит плохо (offline,
   ошибки, загрузка, истёкшая сессия).

## I. Проход по правилам ponytail (все изменённые файлы)

Практики [ponytail](https://github.com/DietrichGebert/ponytail), которые применяю:

- порядок важности: корректность → безопасность → нагрузка → тесты → скорость → компактность;
- у каждой находки — конкретный случай «такой вход → такой неверный результат»;
- делить по задачам, а не по длине; не плодить хелперы ради укорачивания функции;
- сознательные упрощения помечать `shortcut: <предел>, <когда пересмотреть>`;
- никогда не срезать валидацию на границах доверия, защиту от потери данных, безопасность и доступность.

**Ожидаемая нагрузка:** Club до 16 участников (Pro), FREE — до 8. Пользователей немного, пока
работает только UAT. По этой нагрузке оцениваю и пункты про масштаб.

**Охват:** просмотрены все 253 изменённых файла. Продакшн-код backend, contracts, config, схема БД,
скрипты и фронтенд прочитаны построчно. SCSS проверен поиском хардкода (цветов нет, только
размеры). Journey-тесты просмотрены бегло; UI mock-спеки построчно не читал — их судьбу решает #27.
